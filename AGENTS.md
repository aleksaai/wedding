# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Product direction

- This is a mobile-first wedding invitation website for Aleksa and Debóra, not a generic wedding template.
- The final text-free hero artworks are `public/assets/wedding-hero-night-mobile-v1.webp` (1080 × 2340) and `public/assets/wedding-hero-night-desktop-v1.webp` (2560 × 1440). They match the approved cards with a photographic Budapest blue-hour scene, deep navy, champagne-gold lights, snow, and restrained motion. The mobile asset preserves the approved card portrait below the text area; the desktop asset is a dedicated 16:9 outpaint. The hero deliberately contains no names, invitation title, or verse. Keep only navigation plus the lower localized RSVP action, and never crop either face behind navigation or the CTA.
- The couple illustration below the details section uses `public/assets/wedding-couple-illustration.webp` (a painted winter scene of Aleksa and Debóra in Hungarian folk dress on Fisherman's Bastion, Parliament and the Chain Bridge behind them, 1672 × 941, source is 16:9 so `object-fit: cover` barely re-crops it). It replaced `wedding-couple-photo.webp` on 2026-08-25, which in turn had replaced `wedding-budapest-photo.webp` on 2026-08-24; both stay in the repo as unused fallbacks. Present it without caption or text overlay: 4:3 below 700px so the two faces stay readable on a phone, 16:9 from 700px up. Because the artwork is a light, warm-toned illustration rather than a dark photograph, the card carries a `--paper-deep` matte instead of the deep navy one, and no saturation or brightness filter — the earlier treatment washed the painting out. Keep the slim champagne-gold line, the restrained shadow, the moderately rounded corners, and the beige paper background of the surrounding section.
- The personal invitation link opens directly at `/<CODE>` (also accept `/i/<CODE>`) without login or code entry. Codes are random, non-sequential, 6–12 character uppercase alphanumeric values. RSVP is a short progressive flow rather than one long form.
- Guests who open only the root website can still complete RSVP. In that generic flow, request and validate the invitation code as the first RSVP gate through `open_wedding_invitation`, before asking attendance or guest-count questions. Personal subpages continue to supply the code invisibly and skip this gate.
- The website supports four complete languages: German (`de`), Hungarian (`hu`), Serbian in Latin script (`sr`), and English (`en`). Each invitation stores its default language in Supabase; `?lang=` overrides it and the manual switch remains available as a fallback.
- Supabase project `hazvuskpuyudotqqdtoy` is the production source of truth. Public visitors never receive direct table grants: the personal page uses the narrow `open_wedding_invitation` RPC and RSVP uses `submit_wedding_rsvp`. RLS restricts table CRUD to the approved admin allowlist. Never put a service-role key or management PAT in frontend code.
- The private guest workspace lives in the same application at `/admin`. It uses Supabase email magic-link authentication and supports invitation creation/editing, category/language/status filters, card/sent/opened tracking, direct-link copy, and response review. Approved emails are `info@aleksa.ai` and `szildebora@gmail.com`. Auth signups are disabled; both accounts must be pre-provisioned, `signInWithOtp` must use `shouldCreateUser: false`, and the UI must verify `is_wedding_admin()` before loading the dashboard.
- Invitation category defaults are canonical: Debi family/friends → Hungarian, Aleksa family → Serbian, Aleksa friends → German, common friends → English.
- Renaming an invitation must never touch its identity. The edit form updates `display_name` and the planning fields only; `code`, `card_generated_at`, `sent_at`, open counters and the RSVP row stay untouched, so the personal link keeps working and printed cards stay valid (the artwork carries the code, never the name). The personal page reads the name live from `open_wedding_invitation`, so a rename shows up on the next page load. Editing is reachable from the pencil in the row, the pencil in the response drawer, and by double-clicking a row.
- Responses can be recorded by the admin as well (decision 2026-08-25): guests also reply by phone, mail or in person, so the drawer at `/admin` carries the same fields as the public RSVP. Writing goes through `admin_upsert_wedding_rsvp` and `admin_clear_wedding_rsvp`, both security definer and gated on `is_wedding_admin()`, so the rsvp row and `responded_at` always match. `wedding_rsvps.source` is `guest` or `admin` and the drawer shows which it was. The admin is deliberately not bound by `max_adults` or `max_children`, only by a 0 to 20 sanity range, and a backup household has to be promoted before a response can be recorded.
- One unplanned adult companion is always allowed (decision 2026-08-24): a guest whose card was written for one person may still bring a partner. `submit_wedding_rsvp` accepts `max_adults - 1` planned companions plus one extra, and `open_wedding_invitation` returns that figure as `adult_limit`. The admin counts anything above `max_adults` in the "Beyond plan" tile.
- Children are never capped by the invitation (decision 2026-08-24). `max_children` is a planning figure for the admin only; the RSVP always offers children and `submit_wedding_rsvp` accepts up to 10 per age bracket regardless of it. Adults stay bound to `max_adults`. The three brackets are stored separately and deliberately do not overlap: `kids_under_3` (0 to 2), `kids_3_to_17` (3 to 17) and `kids_18_plus` (18 and older, counted as an adult for catering). `children_count` stays as their sum so older reads keep working, and the admin shows the split plus an "Extra kids" total for everything beyond what was planned.
- Yellow spreadsheet rows are reserve guests, not active invitees. Store them as `is_backup = true` and show them only in the admin Backup list. They do not count toward active invitation/people totals, their links and RSVP RPC access stay disabled, and they become normal invitees only after an admin explicitly moves them to the Guest list.
- The approved print-card sources are the eight dark-blue photo designs in `public/assets/cards/`: DE/EN/HU/SR front and back. Every side is exactly 1417 × 2126 px, 2:3, 300 dpi (120 × 180 mm). The original 9:16 fronts were proportionally enlarged and extended only at the narrow left/right margins; the central couple and localized typography remain unchanged and must never be stretched or cropped. The admin preview, print flow, and downloads must preserve the shared 2:3 format.
- Each approved back contains a localized invitation-code heading and a dedicated code slot. The public base assets must never contain a real invitation code. The user-facing preview, print flow, and personalized back-image download render only the selected invitation's existing `wedding_invitations.code` into that slot. The downloaded 1417 × 2126 PNG retains 300 dpi metadata. Active invitations have cards available immediately; backup invitations must never show or generate a card until promoted.
- Card downloads are named after the guest, not the database: `<name>_einladung_front.png` and `<name>_einladung_back.png` (decision 2026-08-24), and the print window's document title is `<name>_einladung` so "Save as PDF" suggests the same name. `slugifyName` strips diacritics and punctuation; the invitation code is appended only when two households share a display name, and it replaces the name entirely if the name slugifies to nothing.
- Admin front and back URLs carry the shared `cardArtworkVersion` cache-busting fingerprint in `src/admin/AdminApp.jsx`. Change that fingerprint whenever any approved card artwork changes so existing admin sessions cannot reuse stale images.
- Canonical event details live in `src/i18n.js`: the couple is addressed by first names only, `Aleksa & Debóra` (decision 2026-08-24, no surnames anywhere in the user-facing site); wedding 23.01.2027; church at Wesselényi utca 53, 1077 Budapest from 14:00; reception at Pollack Mihály tér 3, 1088 Budapest from 17:00; RSVP deadline 31.10.2026; contact `szildebora@gmail.com` / `+36 20 346 7329`. Keep shared addresses, map URLs, website, email, and phone centralized in `eventDetails`; keep user-facing copy localized in all four translation objects.

## Local credentials

- The Wedding Supabase Management API access token is stored locally in macOS Keychain, account `wedding-project`, service `supabase-wedding-access-token`. Retrieve it only at runtime with `security find-generic-password -w -a wedding-project -s supabase-wedding-access-token`; never copy the value into Markdown, source code, frontend environment variables, or Git.
